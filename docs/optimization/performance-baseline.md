P50 为中位数，P95 使用 nearest-rank。小样本的 P95 接近或等于最大值，属于本机短时基线，不能外推为服务等级。CPU 按 24 个逻辑处理器归一化至整机 0–100%。RSS 为进程工作集之和，进程之间的共享页面可能重复计入；另保留 Private Bytes。采样约每 500ms 一次，显存约每秒一次，短暂峰值可能遗漏。

脚本均为仓库外置审计辅助，位于 artifacts 本轮目录。它们通过现有接口调用已有程序，没有改动业务实现。测试写入只发生于隔离副本。正式库只读检查使用 mode=ro 和 query_only，不执行迁移、ANALYZE、VACUUM、checkpoint 或重建。

## IPC、查询与检索

以下为 WebView 调用至返回的端到端时间，包含 CDP 调用包装、IPC、Rust、序列化，不是单独的数据库耗时。

最后两项只反映应用编排、SQLite 和回环协议成本。固定向量和固定回答**没有调用真实模型**，不代表 Embedding 或模型速度。预览样本很小，也不代表大型 RAG 库。

[数据库只读记录](../../artifacts/phase-g0-2026-11-18/databases.json) 中，正式 schema 7 库只有 2 个知识节点。审计用简化列表 SQL 的 30 次暖查询，知识 P50/P95 为 0.0162/0.0257ms，会话为 0.0127/0.0415ms，执行为 0.0152/0.0228ms。这不是完整业务列表接口的计时。EXPLAIN 显示使用工作区索引，部分排序使用临时 B-tree。目前没有慢 SQL 的实测证据；这些数字不支持直接更换数据库或添加整套索引。SQL 计时与 IPC 计时使用不同数据库和调用层，不相减推断某一层成本。

## 直接可定位的请求放大

- 折叠的手动资料选择器会逐条读取当前知识的完整详情。1000 条合成有效知识产生 1000 次 get_knowledge。计数发生在进入聊天/切页准备期间，不把它们全算作图谱本身的查询。
- 图谱从 200 加载到 1000 节点，节点分页为 1+2+3+4+5=15 次，另有 5 次关系查询。代码与请求计数相互吻合。保持同一快照的已加载前缀，可将节点分页的结构性目标设为 5 次。
- 完整调用序列、时间和截图保留在 frontend-verified.json、frontend-final.png。最初 frontend.json 的长会话选择器和部分计时有误，未用于本报告结论；修正辅助脚本后重新采集，没有修改产品代码。

## 对照规则

G1 每个切片沿用固定数据、脚本和统计方法，记录代码版本、构建配置、数据 hash、首轮与稳态、样本数及异常。先验证输出、顺序、用途隔离和历史数据一致，再判断延迟/资源收益；没有显著收益的改动不以“已优化”发布。真实模型推理仍需每批弹窗确认。
