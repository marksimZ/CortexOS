## 编程与工具的执行边界

推荐经用户授权配置Docker Linux运行时，镜像按实际核实的digest固定。只运行数据集支持的纯函数，测试输入由可信控制器传入，预期输出和最终判分留在容器外；不把可修改的自报“passed”作为结果。

容器候选限制：无网络、非root、只读根文件系统、受限临时目录、drop capabilities、禁止提权、1 CPU、256MiB内存、64进程、10秒墙钟、64KiB输出及有限测试数量。代码通过结构化数据/受控临时文件输入，不拼接shell；无宿主工作目录、密钥、GPU或Docker socket挂载。只终止本尝试拥有的容器ID。镜像准备和运行时配置单独授权，资源限制须在实际Windows后端验证。

容器不是绝对安全保证；先做访问宿主/联网/进程滥用/超时/超输出的隔离验收。普通Python子进程、`-I`、超时或Job Object本身不提供完整不可信代码隔离。未配置合格环境的10题标记blocked，保留总计划中的未运行覆盖，不能把静态审查替代“代码测试通过率”。依据：[Docker安全](https://docs.docker.com/engine/security/)、[资源限制](https://docs.docker.com/engine/containers/resource_constraints/)、[无网络模式](https://docs.docker.com/engine/network/drivers/none/)。

工具题只允许固定模拟函数及已声明参数，由可信评分器校验工具名称、JSON形状和语义值。Phase 1衡量“工具选择和参数正确率”，不声称已测多步工具工作流；真实外部动作没有权限。后续多步实验再增加有上限的调用序列及实际执行关联。

## RAG评分与增强实验

Phase 1的10题把固定资料作为题目材料发送，不调用生产知识检索，因此衡量“给定材料下回答与引用能力”。每个待回答事实有人工定义的标准值和可支持它的材料/行区间，评分器检查“事实值正确且引用命中该事实的允许支持集合”。仅命中现有行或文字相似不能算支持。

分别报告事实准确率、引用定位有效率、引用支持率和必需事实覆盖率；不可回答题的正确拒答单独评分。自由文本超出确定性规则时标记需人工复核，不随意判成支持。现有`citations.rs::check`可提供生产引用定位，但不承担语义支持判分。

Phase 3才做真实CortexOS A/B：同一模型身份、问题、输出上限和评分规则，A不带额外知识/记忆，B从固定知识版本及检索快照准备上下文。记录候选、排除、最终材料、原始请求和真实执行ID。旧知识版本用实验副本，不修改生产生效指针。当前未实现的长期记忆、压缩、向量重排或验证工作流不列为已启用因素。

A/B先只改变一个因素，后续才组合；轮换顺序并保存排程种子。成对比较每道题、每次重复的分差、延迟差和失败案例，允许增强变差或无改善，不预设结论。

## 指标口径

| 指标 | 计算与来源 | 必须展示的限制 |
| --- | --- | --- |
| 正确率/评分 | 每类正确项或规则分数 / 已完成有效评分项 | 同时列已评分/计划项、unsupported/blocked/失败；不隐藏不支持项后给出完整60题结论 |
| 计划任务通过率 | 满足该题通过规则的逻辑项 / 全部计划逻辑项 | 答错、失败与未运行分别展示；重试不扩充分母 |
| 代码通过率 | 通过断言数/总断言及全通过题数/可评分代码题 | 隔离环境不就绪显示未运行，不能记为通过或当答案错误 |
| JSON/工具指标 | 格式合规、语义正确、工具名/参数分别判断 | 普通文本提示JSON与原生结构化约束分成不同配置 |
| 客户端首输出延迟 | 单调时钟首次发送开始→首个非空正文增量 | 标注“首个可见文字”；不是内部首Token。工具首事件另记；没有可见文字为不可用 |
| 客户端响应/端到端 | 发送→终态；逻辑项开始→结果落盘分别计时 | 排队、模型检查、加载、评分和持久化分项；不与服务端total_duration混用 |
| 服务端TPS | eval_count / (eval_duration_ns / 1e9) | 指标缺失、时长≤0时不可用；流帧数或中文字数不是Token数 |
| Prompt/加载耗时 | Provider真实返回的prompt_eval_duration/load_duration | 切片5已采集；缺失不从total差值猜测 |
| 冷/热条件 | 卸载确认后的首次请求；已加载确认后的后续请求 | 预加载操作单独记录，不能声称清空OS/磁盘/缓存；云端不显示本机冷加载指标 |
| 失败/超时 | 失败尝试/已发送尝试，超时为其中明确子类 | 首次与重试均保留；评分失败与模型失败分开 |
| GPU峰值 | 明确采样区间内整卡memory.used样本最大值 | 标记“采样峰值”，含系统/其他程序；/ps size_vram是不同来源的模型估计 |
| CPU/RAM | 可确认进程的CPU时间差/墙钟与工作集，或明确整机值 | 多核归一方式、进程范围、采样周期和缺样率进入详情 |
| Token | Provider最终确认的输入/输出/缓存等计数 | 客户端估算另列，未知为null；不同模型分词器的Token数非相同文字量 |

切片5已补充客户端首输出、Prompt处理时间及本地资源采样，实际字段和范围见[指标交付](benchmark-metrics-slice5.md)。历史缺失时刻保持未知，不从事件墙钟近似回填精确TTFT。

资源默认1秒采样，记录相对时间、范围和失败原因；短请求可能只有少数样本。不能把采样峰值等同连续真实峰值，或把当前711MiB空闲时整卡读数写成模型资源结论。相关字段和单位参考[NVIDIA SMI官方文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

## 费用和统计

输入/输出、缓存和额外收费项逐项按本次价格快照估算，总费用包含预热（若实际收费）、失败和重试。每个成功任务平均费用=全部已确认估算费用/成功逻辑项数；成功数为0或存在未决收费时，显示不可计算或有上下界的区间。单位质量成本仅在明确非零评分单位下提供，不与其他量纲混成排行榜总分。

本地API单价与设备电力成本分开：可说明没有第三方推理API费，不能据此断言总成本为0。云端估算不是供应商实际账单，未确认费用不能计零；价格获取时间、币种、单位和版本随报告导出。详见[Provider预算设计](benchmark-provider-design.md)。

标准对比推荐每题3次独立重复；快速检查可选1次，明确样本量不足。四模型×60题×3次为720个逻辑项，启动前展示，不在本轮执行。按模型分组并记录顺序、预加载和条件；比较使用相同题目、模板、材料、参数公共能力及输出预算。

单调计时保存原始值，汇总每类n、p50/p95及失败分布。小样本的p95不当稳定吞吐保证。Phase 3对同题成对分差做区间估计并记录方法/随机种子；题目与重复的层级不能混成大量独立样本来夸大置信度。seed相同也不保证位级确定性。

主比较默认使用每个计划逻辑项的首次尝试，重试/恢复后的最终完成率另列；不挑最高分尝试。达到输出Token上限、采集缺失和人工复核均保留明确标记；评分器版本不一致时先选定同一版本离线重算，再比较已有原文。

## 报告、复算与验收

JSON含schema版本、实验清单/hash、数据集/评分器/模型/硬件身份、原始输入输出、实际参数、指标来源与缺失、所有尝试及引用依据；报告不包含密钥或HTTP认证头。CSV输出逐题指标、状态及覆盖率，正确转义，并处理表格公式注入；详细原文优先JSON。导出由Rust原生保存对话框写入用户明确选择的位置。

评分器可在无模型调用情况下复算已有回答，新增评分版本并显示规则差异。标准答案/schema/容差/材料任一变化都改变评分版本或数据集版本。

Phase 1验收先用受控响应验证正确/错误/缺字段/工具调用/取消/重启和计数，再用至少两个真实本地模型身份跑完整计划并检查原文与逐题评分。四家模型和全部代码题通过需模型及隔离环境就绪；若仅Qwen双标签可测，报告明确限制，不称为四家基准。不因Phase 0构建通过或现有150%人工验收而宣称新增评测UI/数据集已经验收。
