## 已实现范围

入口：评测 → 项目适配 → 4.测试任务 → 编程任务草案。复用当前布局，默认折叠。选择已有项目快照，或通过系统选择器导入项目文件夹/ZIP；沿用安全扫描上限、敏感内容/链接排除及只读保存。

1. 选择固定分析版本、项目Python文件及最多120行/24KB原函数范围。保存后来源不可替换；更换范围需另建草案。
2. 明确标记“我确认的功能需求”或“已报告的故障（尚待复现）”，填写依据和预期行为；没有自动编造Bug或用模型认定正确。
3. 定义有效函数名、1–5个命名参数及返回类型。首版支持整数、文本、布尔值及同类型列表；复用Python3.13、严格类型、输入不可修改的既有评分合同。整数限±9007199254740991，列表最多128项，文本最多4096字符。
4. 定义7–32组不同输入，包含目标行为、边界情况和非目标回归。参数为JSON数组，输出为对应类型的JSON值。后端拒绝重复/冲突输入、缺失分类或错误类型；分类是否合理、覆盖是否充分仍由人工和后续执行验证。
5. 保存参考实现和错误实现；原代码直接来自快照，作为无修改对照。三份代码均作为文本，不在宿主机解析执行；静态阶段只检查非空、大小及原文是否相同。
6. 保存追加修订，历史只读，保留来源/题目/实现/用例及指纹；过期修订拒绝覆盖。切页保留当前会话内草稿，关闭提醒及放弃确认沿用现有交互；已保存修订在重载后从SQLite读取。

## 存储与权限

新增后端`benchmark/harness/programming.rs`，复用`tasks::checked_snapshot`、`dataset::validate_runtime_case`、`cases::seal`及`python::policy`。没有第二套运行器。编程草案仅使用已有generation_jobs/cases，以`harness_programming_drafts`隔离；不插入benchmark_cases/datasets/reviews或execution_runs。计划及候选沿用既有不可变触发器，更新通过追加版本完成。schema仍11，历史迁移不变。

两个窄业务命令：`get_harness_programming_drafts(workspaceId,jobId?)`、`save_harness_programming_draft(workspaceId,{jobId?,expectedRevision,origin,spec})`。读取严格限定工作区、用途、版本和hash。新增精确的两项应用能力，不新增通用文件、终端、模型或Docker权限。普通个性化、D2a只读任务及旧Runner均不接受此用途，故无法通过原发布命令绕过验证。
